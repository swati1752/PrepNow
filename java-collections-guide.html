1   The Big Picture

The Java Collections Framework lives in java.util. Everything stems from two root interfaces:

📦

Collection<E>

A group of individual elements — List, Set, Queue

🗂️

Map<K, V>

Key-value pairs — does NOT extend Collection

2   Complete Hierarchy Diagram

3   List — Ordered & Indexed

Elements have a position (index). Duplicates allowed. Maintains insertion order.

⚡

ArrayList

Backed by: dynamic array

✅ Use when you need fast random access by index and most operations are reads.

  • get(i) → O(1)
  • add (end) → O(1) amortized
  • add/remove (middle) → O(n)
  • Not synchronized

Most used List

🔗

LinkedList

Backed by: doubly-linked list

✅ Use when you do frequent insertions/deletions at the beginning or middle.

  • get(i) → O(n)
  • add/remove (head/tail) → O(1)
  • Also implements Deque
  • Higher memory (node pointers)
🔒

Vector / Stack

Legacy — synchronized

❌ Avoid in new code. Use ArrayList + Collections.synchronizedList() or CopyOnWriteArrayList.

  • Vector = synchronized ArrayList
  • Stack extends Vector (LIFO)
  • Use ArrayDeque instead of Stack

💡 ArrayList vs LinkedList — Quick Rule

95% of the time, use ArrayList. LinkedList is only better when you're constantly adding/removing from the head and never doing random access. In practice, ArrayList's cache locality makes it faster for almost everything.

4   Set — No Duplicates

Each element appears only once. Uses equals() and hashCode() to determine uniqueness.

🏷️

HashSet

Backed by: HashMap

✅ Use when you need fast lookup / uniqueness and don't care about order.

  • add, remove, contains → O(1)
  • No order guaranteed
  • Allows one null

Most used Set

📎

LinkedHashSet

Backed by: LinkedHashMap

✅ Use when you need uniqueness + insertion order preserved.

  • Slightly slower than HashSet
  • Maintains insertion order
  • Iteration = insertion order
🌲

TreeSet

Backed by: TreeMap (Red-Black tree)

✅ Use when you need elements sorted automatically.

  • add, remove, contains → O(log n)
  • Sorted by natural order or Comparator
  • No null (throws NPE)

Set Decision Flowchart

Need unique elements?
  │
  ├── Don't care about order?  ──────────►  HashSet       (fastest)
  │
  ├── Need insertion order?    ──────────►  LinkedHashSet (ordered)
  │
  └── Need sorted order?       ──────────►  TreeSet       (sorted, slower)

5   Queue & Deque — FIFO / LIFO

Queue = First-In-First-Out. Deque = Double-Ended Queue (can act as both Queue and Stack).

📊

PriorityQueue

Backed by: binary heap

✅ Use when you need elements processed by priority (min or max).

  • offer/poll → O(log n)
  • peek → O(1)
  • Default = min-heap (natural order)
  • NOT thread-safe
↔️

ArrayDeque

Backed by: resizable circular array

✅ Use as both Stack (LIFO) and Queue (FIFO). Faster than LinkedList for both.

  • push/pop/offer/poll → O(1)
  • No capacity restrictions
  • No null elements

Replaces Stack & LinkedList-as-Queue

🔗

LinkedList (as Queue)

Also implements Deque

⚠️ Use only when you need a Deque with null elements (ArrayDeque doesn't allow nulls).

  • offer/poll → O(1)
  • Slightly more memory overhead
  • Allows null

6   Map — Key-Value Pairs

Stores data as key → value pairs. Keys are unique. Does NOT extend Collection.

🗃️

HashMap

Backed by: array of buckets + linked list / tree

✅ Use when you need fast key-based lookup and don't care about order.

  • put, get, remove → O(1) average
  • No order guaranteed
  • Allows one null key, multiple null values
  • Not synchronized

Most used Map

📎

LinkedHashMap

Backed by: HashMap + doubly-linked list

✅ Use when you need key-value storage + insertion order preserved (or access order for LRU cache).

  • Same O(1) as HashMap
  • Iteration = insertion order
  • Can be configured for access-order (LRU)
🌲

TreeMap

Backed by: Red-Black tree

✅ Use when you need keys sorted automatically.

  • put, get, remove → O(log n)
  • Sorted by natural key order or Comparator
  • No null keys
  • Provides firstKey(), lastKey(), subMap()
🔒

Hashtable

Legacy — fully synchronized

❌ Avoid. Use ConcurrentHashMap instead for thread safety.

  • Synchronized on every method
  • No null keys or values
  • Extends Dictionary (obsolete)
⚡

ConcurrentHashMap

Thread-safe, segment-level locking

✅ Use when you need a thread-safe Map with high concurrency.

  • Lock striping → much faster than Hashtable
  • No null keys or values
  • From java.util.concurrent
🏷️

EnumMap

Backed by: array indexed by enum ordinal

✅ Use when keys are enum constants. Fastest possible Map for enums.

  • All operations → O(1)
  • Extremely compact
  • Keys must be a single enum type

Map Decision Flowchart

Need key-value pairs?
  │
  ├── Keys are enums?           ──────────►  EnumMap            (fastest for enums)
  │
  ├── Need thread safety?       ──────────►  ConcurrentHashMap  (modern, concurrent)
  │
  ├── Need sorted keys?         ──────────►  TreeMap            (O(log n), sorted)
  │
  ├── Need insertion order?     ──────────►  LinkedHashMap      (ordered)
  │
  └── Just fast lookup?         ──────────►  HashMap            (O(1), most common)

9   Common Pitfalls

❌ Using Stack class

Stack extends Vector (synchronized, legacy). Use ArrayDeque as a stack instead.

❌ Forgetting hashCode() with HashSet/HashMap

If you override equals(), you MUST override hashCode(). Otherwise duplicates sneak in.

❌ Modifying keys after insertion

Changing a key's fields after putting it in a HashMap corrupts the bucket. The entry becomes unfindable.

❌ ConcurrentModificationException

Don't add/remove from a collection while iterating with a for-each. Use Iterator.remove() or CopyOnWriteArrayList.

❌ Null in TreeSet / TreeMap

TreeSet/TreeMap use compareTo(), which throws NPE on null. No nulls allowed.

❌ Hashtable for thread safety

Hashtable locks the entire table. ConcurrentHashMap is far more performant with segment-level locks.

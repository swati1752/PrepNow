How to use this guide

Answer structure: define the concept → explain how it works → give a real implementation example → mention trade-offs → explain how you would troubleshoot it.

For scenario questions, avoid claiming that one technology solves everything. State assumptions, identify bottlenecks, describe safeguards and explain how you would measure whether the solution worked.

Important: A Senior Associate Consultant interview may test ownership and communication as much as syntax. Be ready to explain your exact contribution, design decisions, testing, deployment and production impact. Never claim tools, scale or results you did not personally work with.

1. Explain your current project architecture

Project discussionMust prepare

Model answer

“I work on a Java backend application built using Spring Boot. The application exposes REST APIs and contains business logic in service components, data access in repository/DAO components, and persistence through relational databases such as SQL Server, PostgreSQL or Oracle, depending on the module and deployment.”

“A typical request enters through the controller, where request data is bound and basic validation is performed. The controller delegates to a service, which applies business rules and coordinates repository calls or integrations with other modules. The repository interacts with the database. The response is returned as a DTO, and common exceptions are translated into consistent HTTP responses through centralized exception handling.”

“For module-to-module integration, I have worked with REST-based communication using RestTemplate. I have also worked on validation, error handling, security remediation, bug fixing and production issue analysis. My explanation of the architecture would distinguish the parts I directly developed from the wider platform.”

Explain the layers

  • Controller: HTTP endpoint, request/response mapping, input validation and status codes. Avoid putting business rules here.
  • Service: business logic, transaction boundary, orchestration and calls to repositories or external services.
  • Repository/DAO: persistence operations and query execution.
  • DTO: API contract. It prevents exposing persistence entities directly and lets the API evolve independently.
  • Cross-cutting components: authentication, authorization, logging, exception mapping, metrics and tracing.

Example request flow

Client
  → API / Controller
  → Request validation
  → Service (business rules)
  → Repository → Database
  → Service builds response DTO
  → Controller returns HTTP response
Likely follow-up questions
  1. Why do you use DTOs instead of returning entities? To control the API contract, avoid exposing internal schema, prevent accidental data leakage and avoid serialization problems such as lazy-loading cycles.
  2. Where should @Transactional be placed? Usually at the service method/class that represents a business transaction, so multiple repository operations can participate in one transaction.
  3. How do you validate requests? Use Bean Validation annotations such as @NotNull, @Size and @Pattern with @Valid, then map validation failures to a clear 400 response.
  4. How do you test each layer? Controller tests for HTTP contract, service unit tests with mocked dependencies, repository integration tests against a representative database, and end-to-end tests for critical flows.
  5. What happens if the database is unavailable? The repository call fails; the exception is logged with correlation context, mapped to an appropriate response, and the service may use bounded retries only when safe. Do not return fake success.

2. How does a request flow in Spring Boot?

Spring MVCMust prepare

Model answer

In a typical Spring MVC application, an incoming HTTP request is received by the servlet container, such as Tomcat, and passed through the servlet filter chain. Spring Security filters may authenticate the request and apply authorization rules. The request then reaches the DispatcherServlet, which acts as the front controller.

  1. Filters: process cross-cutting concerns such as security, CORS, request logging and correlation IDs.
  2. DispatcherServlet: coordinates request processing.
  3. HandlerMapping: identifies the controller method matching the URL and HTTP method.
  4. HandlerAdapter: invokes the selected controller method.
  5. Argument resolution: binds path variables, query parameters, headers and request bodies. JSON is commonly converted using Jackson message converters.
  6. Controller and service: application code executes business logic and persistence/integration work.
  7. Response conversion: the return value is serialized, usually to JSON, and written to the HTTP response.

Exceptions can be resolved by Spring MVC exception resolvers, including methods annotated with @ExceptionHandler in a @RestControllerAdvice.

Example

@RestController
@RequestMapping("/api/orders")
class OrderController {
    private final OrderService service;

    OrderController(OrderService service) {
        this.service = service;
    }

    @PostMapping
    ResponseEntity<OrderResponse> create(
            @Valid @RequestBody CreateOrderRequest request) {
        return ResponseEntity.status(HttpStatus.CREATED)
                .body(service.create(request));
    }
}
Likely follow-up questions
  1. What is DispatcherServlet? Spring MVC's central servlet that dispatches requests to handlers and coordinates response processing.
  2. Filter vs HandlerInterceptor? A filter belongs to the servlet layer and can wrap requests before they reach Spring MVC. An interceptor runs within Spring MVC around handler execution and has access to handler information.
  3. @RequestBody vs @RequestParam? @RequestBody binds the request body, commonly JSON. @RequestParam binds query/form parameters.
  4. What is HttpMessageConverter? It converts HTTP request/response bodies to Java objects and back, for example JSON through Jackson.
  5. Where does validation happen? During argument binding when Bean Validation is triggered with @Valid or @Validated; validation exceptions should be mapped to useful client errors.

3. How does HashMap work internally?

Core JavaMust prepare

Model answer

HashMap stores key-value pairs in an array of buckets. It uses the key's hashCode() to calculate a bucket index. If multiple keys map to the same bucket, a collision occurs. Java handles collisions using a linked structure; in modern Java implementations, a heavily populated bucket can be converted into a balanced tree when implementation thresholds and capacity conditions are met.

At a high level, the hash is spread and an index is calculated using the table capacity (conceptually (n - 1) & hash when capacity is a power of two). The map then checks keys using hash and equality. A key must obey the contract: if two objects are equal according to equals(), they must return the same hashCode().

Important points

  • Average get/put performance is approximately O(1) with a good hash distribution; collisions can make operations slower.
  • Default load factor is 0.75 in the standard implementation. When size crosses the threshold, the table resizes.
  • HashMap allows one null key and multiple null values.
  • HashMap is not thread-safe. Concurrent updates require synchronization or a concurrent collection such as ConcurrentHashMap.
  • Do not mutate fields used in a key's hashCode/equals after inserting it; lookup may no longer find the entry.

Example

Map<String, Integer> counts = new HashMap<>();
counts.put("java", 2);
counts.put("spring", 1);
int value = counts.getOrDefault("java", 0);
Likely follow-up questions
  1. What if two keys have the same hash code? They land in the same bucket; HashMap compares keys using equals to distinguish them.
  2. Why override equals() and hashCode() together? Hash-based collections first use the hash to locate a bucket and then equality to identify the key. Violating the contract can cause failed lookups or duplicate logical keys.
  3. HashMap vs ConcurrentHashMap? HashMap is not thread-safe. ConcurrentHashMap supports concurrent access and disallows null keys/values, avoiding ambiguity in concurrent retrieval.
  4. What is load factor? It controls the occupancy threshold that triggers resizing. A lower factor uses more memory but can reduce collisions; a higher factor saves space but may increase collisions.
  5. Can a mutable object be a key? Technically yes, but it is dangerous if fields used by equals/hashCode change after insertion. Prefer immutable keys.

4. How does an API Gateway work?

MicroservicesMust prepare

Model answer

An API Gateway is the single entry point for clients calling a group of backend services. Instead of a mobile or web client knowing every internal service address, it calls the gateway. The gateway routes the request to the appropriate service and can centralize cross-cutting concerns.

Common responsibilities include routing, TLS termination, authentication/authorization integration, rate limiting, request-size limits, CORS, load balancing integration, request/response transformation and observability. Business rules should generally remain in the relevant domain service rather than becoming tightly coupled to the gateway.

   API Gateway

Benefits and trade-offs

  • Hides internal topology and simplifies client integration.
  • Provides a central place for edge security and traffic policies.
  • Can reduce client-side orchestration.
  • It becomes a critical component, so deploy it redundantly and monitor latency, errors and saturation.
  • A poorly designed gateway can become a bottleneck or accumulate business logic.
Likely follow-up questions
  1. API Gateway vs load balancer? A load balancer distributes traffic among instances. A gateway commonly adds API-aware routing and policies such as authentication, throttling and transformations. Products may combine capabilities.
  2. What if the gateway goes down? Run multiple instances across failure zones, use health checks and resilient infrastructure, and monitor the gateway itself.
  3. Where should JWT validation happen? It can happen at the gateway for early rejection and again at services when services must independently enforce authorization. Trust boundaries and token propagation must be designed carefully.
  4. What is rate limiting? Restricting request volume per client/key/IP/time window to protect services and ensure fair usage.

5. How do microservices communicate?

Microservices

Model answer

Microservices commonly communicate synchronously or asynchronously. In synchronous communication, one service calls another and waits for a response, usually over HTTP/REST or gRPC. In asynchronous communication, a service publishes a message or event to a broker such as Kafka or RabbitMQ, and another service consumes it independently.

ApproachGood fitTrade-off
REST / HTTPSimple request-response APIs and broad interoperabilityCaller depends on callee availability and latency
OpenFeignDeclarative HTTP clients in Spring Cloud ecosystemsStill synchronous HTTP; timeouts/retries remain essential
WebClientReactive/non-blocking HTTP workflowsRequires understanding reactive composition and backpressure
MessagingEvents, decoupling and background workflowsEventual consistency, duplicate delivery and ordering concerns

Choose based on latency, coupling, delivery guarantees, throughput and business consistency requirements—not simply because a system is labelled microservices.

RestTemplate example

HttpHeaders headers = new HttpHeaders();
headers.setContentType(MediaType.APPLICATION_JSON);
HttpEntity<CreateRequest> entity =
        new HttpEntity<>(request, headers);

ResponseEntity<Result> response =
        restTemplate.exchange(url, HttpMethod.POST,
                entity, Result.class);

Configure connection/read timeouts, handle non-2xx responses, avoid logging secrets and use bounded retries only for operations that are safe to retry.

Likely follow-up questions
  1. RestTemplate vs WebClient? RestTemplate is a synchronous blocking client. WebClient supports non-blocking reactive I/O and can also be used in ways that return a response synchronously, though blocking defeats its reactive benefits.
  2. What is OpenFeign? A declarative HTTP client where an interface describes the remote API; framework integration creates the implementation.
  3. When would you use Kafka? For event-driven workflows, high-throughput streams or decoupling producers from consumers—not for every simple request-response call.
  4. How do you version APIs? Use a deliberate compatibility strategy such as additive changes, versioned paths/headers where needed, deprecation windows and contract tests.
  5. How do you avoid tight coupling? Keep service contracts stable, share contracts rather than internal implementation, avoid direct database sharing and use events where asynchronous decoupling is valuable.

6. What happens if one microservice goes down?

ResilienceMust prepare

Model answer

If Service A synchronously calls Service B and B is unavailable, A may experience connection failures, timeouts or thread/resource exhaustion if calls wait too long. I would prevent the failure from spreading by setting connection and response timeouts, using a circuit breaker, applying bounded retries with backoff and jitter where safe, limiting concurrent calls and defining a fallback only when the business can tolerate it.

Circuit breaker states

  • Closed: calls flow normally while failures are monitored.
  • Open: calls fail fast after the configured failure threshold is reached.
  • Half-open: a limited number of trial calls are allowed to check whether the dependency recovered.

For asynchronous messaging, the consumer can retry transient failures, move repeatedly failing messages to a dead-letter queue and support safe replay. Idempotency is important because a message may be delivered more than once.

Resilience4j-style illustration

@CircuitBreaker(name = "inventory", fallbackMethod = "fallback")
public Inventory getInventory(String sku) {
    return inventoryClient.getInventory(sku);
}

public Inventory fallback(String sku, Throwable ex) {
    // Return a business-approved degraded response,
    // or propagate a controlled service-unavailable error.
    throw new DependencyUnavailableException(
        "Inventory service is temporarily unavailable", ex);
}

The fallback method signature must be compatible with the original method and include the exception parameter. Exact configuration depends on the Resilience4j/Spring integration version.

Likely follow-up questions
  1. Retry vs circuit breaker? Retry repeats an operation for transient failure. Circuit breaker stops calls when a dependency is unhealthy. Unbounded retries can amplify an outage.
  2. What is a timeout? A maximum wait for connection establishment or response. Separate connect and read/response timeouts may be configured.
  3. What is bulkhead? Isolation of resources, such as separate thread pools or concurrency limits, so one slow dependency cannot consume all capacity.
  4. Should every failure trigger retry? No. Retry transient failures such as selected network errors or 503 responses. Do not blindly retry validation errors or non-idempotent writes.
  5. What is a fallback? A controlled degraded response or alternate path. It must not falsely report that a critical transaction succeeded.

7. How does @Transactional work?

SpringMust prepare

Model answer

@Transactional declares that a method should execute within a transaction managed by Spring. In the common proxy-based model, a call through the Spring proxy starts or joins a transaction, invokes the method, and then commits or rolls back according to the configured rules.

By default, Spring rolls back on unchecked exceptions (RuntimeException and Error), but not generally on checked exceptions. You can customize this using rollbackFor. The annotation is most useful at a service-layer method that groups related database operations into one business unit.

Example

@Service
class TransferService {
    @Transactional
    public void transfer(Long from, Long to, BigDecimal amount) {
        accountRepository.debit(from, amount);
        accountRepository.credit(to, amount);
    }
}

If the credit operation fails with a rollback-triggering exception, the debit should also be rolled back—assuming both operations participate in the same transaction manager and transactional resource.

Important caveats

  • Self-invocation (one method calling another method on the same object) typically bypasses the proxy, so the inner method's transactional annotation may not take effect.
  • Private methods are not normally intercepted by standard proxy-based transaction management.
  • Do not keep database transactions open while making slow external HTTP calls unless there is a carefully justified design.
  • Transactions across multiple independent microservices are not made atomic merely by annotating one method.
Likely follow-up questions
  1. What is propagation? It defines how a method participates in an existing transaction. REQUIRED joins or creates one; REQUIRES_NEW suspends the current transaction and starts a new one.
  2. What is isolation? It controls visibility of concurrent transaction changes and helps manage anomalies such as dirty reads, non-repeatable reads and phantom reads.
  3. Checked exception rollback? Configure @Transactional(rollbackFor = Exception.class) when that is the intended policy.
  4. Can @Transactional be used on a controller? It can, but service-layer boundaries usually better represent business transactions and keep web concerns separate.
  5. How do you handle transactions across microservices? Often with a Saga: a sequence of local transactions with compensating actions, or other workflow patterns. It is not the same as a single ACID transaction.

8. How do you handle production 500 errors?

TroubleshootingMust prepare

Model answer

I first establish scope and impact: which endpoint, when it started, how many users/requests are affected, and whether the issue is isolated to one instance or common to all instances. I correlate the request ID or trace ID across application and dependency logs, inspect the stack trace and identify the first meaningful application frame rather than focusing only on the final wrapper exception.

  1. Reproduce using the same request, environment and relevant data if safe.
  2. Check recent deployments, configuration changes, dependency changes and infrastructure events.
  3. Inspect application logs, metrics, traces, database connectivity, thread pools, memory and downstream service health.
  4. Identify root cause and assess whether rollback, feature disablement or a targeted fix is safest.
  5. Implement a fix, add regression tests, validate in a lower environment and deploy through the release process.
  6. Monitor after deployment and document root cause, impact, corrective and preventive actions.

In my project experience, production debugging and issue resolution involved analyzing logs, tracing the affected module, checking request data and dependencies, and delivering fixes with regression coverage. Give one specific incident you personally handled, including what you checked and how you confirmed the fix.

Centralized exception handling example

@RestControllerAdvice
class GlobalExceptionHandler {
    @ExceptionHandler(EntityNotFoundException.class)
    ResponseEntity<ApiError> notFound(EntityNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ApiError("RESOURCE_NOT_FOUND", ex.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    ResponseEntity<ApiError> generic(Exception ex) {
        // Log full exception with correlation ID internally.
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(new ApiError("INTERNAL_ERROR",
                                   "An unexpected error occurred"));
    }
}
Likely follow-up questions
  1. What is the difference between 4xx and 5xx? 4xx generally indicates a client/request problem; 5xx indicates the server failed to fulfil a valid request or a dependency/server problem occurred.
  2. Would you expose the stack trace to the client? No. Return a safe error code/message and log diagnostic detail securely on the server.
  3. What if logs do not show the root cause? Add correlation IDs, structured contextual logging, metrics and distributed tracing; reproduce with controlled diagnostics and inspect dependency/infrastructure telemetry.
  4. What is RCA? Root Cause Analysis: establish the underlying cause, not merely the symptom, and define corrective and preventive actions.
  5. How do you avoid logging sensitive information? Mask tokens, passwords, personal data and secrets; restrict log access and retention.

9. How would you optimize a slow API?

PerformanceMust prepare

Model answer

I would measure before changing code. First capture endpoint latency percentiles (especially p95/p99), throughput, error rate and resource utilization. Then break down the request time into application processing, database queries, external calls, serialization and network time using traces or targeted timings.

  • Database: inspect slow query plans, indexes, joins, N+1 queries, locks and connection-pool saturation.
  • Application: remove redundant work, reduce object creation where material, optimize algorithms and avoid unnecessary serialization.
  • External calls: set timeouts, parallelize independent calls only when safe, and use caching where data freshness permits.
  • Capacity: review thread pools, connection pools, CPU, heap and garbage collection.
  • Validation: load test with realistic traffic and compare p50/p95/p99, throughput and error rate before and after.

For example, if an endpoint is slow because it runs an unindexed filter query, adding an appropriate index may help—but confirm with the execution plan and check the write overhead and index selectivity.

JMeter example talking point

If you have used Apache JMeter, explain the test plan, number of concurrent virtual users, ramp-up period, duration, data used, measured response times and how you identified the bottleneck. Be precise about whether the reported improvement was response time, throughput or both.

Likely follow-up questions
  1. What is an N+1 query problem? One query fetches a list, then an additional query is executed for each item. Fix with suitable fetch joins, entity graphs, batch fetching or a purpose-built query.
  2. What is caching? Storing frequently accessed data for reuse. Consider TTL, invalidation, consistency, cache stampede and whether the data is safe to share.
  3. How do you identify a slow SQL query? Use query logs/monitoring and the database execution plan; inspect scans, joins, cardinality estimates, indexes and lock waits.
  4. What is p95 latency? 95% of measured requests completed at or below that duration; it reveals tail latency better than average alone.
  5. Does adding more threads always improve performance? No. It can increase contention and overwhelm downstream resources. Tune based on CPU, blocking behavior and dependency capacity.

10. SQL: Find the third-highest salary per department

SQLCoding

Model answer using DENSE_RANK

Assume an Employee table with employee_id, name, department_id and salary. If “third-highest salary” means the third distinct salary in each department, use DENSE_RANK() partitioned by department.

WITH ranked AS (
    SELECT
        employee_id,
        name,
        department_id,
        salary,
        DENSE_RANK() OVER (
            PARTITION BY department_id
            ORDER BY salary DESC
        ) AS salary_rank
    FROM Employee
)
SELECT employee_id, name, department_id, salary
FROM ranked
WHERE salary_rank = 3;

Why DENSE_RANK? Equal salaries receive the same rank, and the next distinct salary receives the next consecutive rank. For example, salaries 100, 100, 90, 80 have dense ranks 1, 1, 2, 3.

FunctionFor values 100, 100, 90, 80
ROW_NUMBER1, 2, 3, 4 (unique sequence)
RANK1, 1, 3, 4 (gaps after ties)
DENSE_RANK1, 1, 2, 3 (no gaps)
Likely follow-up questions
  1. What if they ask for the third employee by salary, not the third distinct salary? Use ROW_NUMBER with a deterministic tie-breaker such as employee_id.
  2. What if a department has fewer than three distinct salaries? It returns no row for that department.
  3. How would you find the second-highest salary overall? Use DENSE_RANK ordered by salary descending and filter rank = 2, or a distinct ordered subquery.
  4. Why use PARTITION BY? It restarts the ranking independently for each department.
  5. Can this be done without window functions? Yes, using correlated subqueries or nested DISTINCT/ORDER BY queries, but window functions are often clearer and more maintainable.

11. Find duplicate elements using Java Streams

Java 8Coding

Model answer

One readable approach is to maintain a Set of values already seen. A value is a duplicate when adding it to the set returns false.

List<Integer> numbers =
        Arrays.asList(1, 2, 3, 2, 4, 1, 5);

Set<Integer> seen = new HashSet<>();

Set<Integer> duplicates = numbers.stream()
        .filter(n -> !seen.add(n))
        .collect(Collectors.toSet());

System.out.println(duplicates); // [1, 2] (order unspecified)

This is O(n) expected time and O(n) additional space. The set is mutated inside the stream, so this is suitable only for a sequential stream in this form; do not change it to parallelStream() without redesigning the operation.

Alternative: frequency map

Map<Integer, Long> frequency = numbers.stream()
        .collect(Collectors.groupingBy(
            Function.identity(),
            Collectors.counting()));

List<Integer> duplicates2 = frequency.entrySet().stream()
        .filter(e -> e.getValue() > 1)
        .map(Map.Entry::getKey)
        .collect(Collectors.toList());
Likely follow-up questions
  1. How do you preserve insertion order? Collect into a LinkedHashSet, or use an ordered frequency approach and preserve the source's encounter order.
  2. How do you count each character in a string? Convert to a character stream and collect with groupingBy plus counting, taking care with Unicode code points if full Unicode support is required.
  3. What is the difference between map and flatMap? map transforms each element into one result; flatMap transforms each element into a stream/collection and flattens the results.
  4. What is a stream? A pipeline for declarative processing of data through intermediate operations (often lazy) and a terminal operation.
  5. Why can stateful stream operations be risky? Shared mutable state can cause race conditions and incorrect results, especially in parallel pipelines.

12. Implement the Singleton design pattern

Design patternsCoding

Model answer: enum Singleton

public enum AppConfig {
    INSTANCE;

    public void printStatus() {
        System.out.println("Application is running");
    }
}

// Usage:
AppConfig.INSTANCE.printStatus();

An enum singleton is concise and protects against several serialization and reflection issues associated with ordinary singleton implementations. In application code, however, Spring's singleton bean scope is often the better choice for managed components.

Alternative: initialization-on-demand holder

public final class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}

Class initialization is thread-safe under Java's initialization guarantees, and the instance is created when the holder is first referenced.

Likely follow-up questions
  1. Why is a simple lazy singleton unsafe? Two threads may both observe a null instance and create separate objects unless initialization is synchronized or otherwise safely published.
  2. What is double-checked locking? A lazy initialization pattern using a volatile field and synchronization to avoid locking after initialization. It must be implemented correctly.
  3. Spring singleton vs Singleton design pattern? Spring singleton means one bean instance per bean definition per application context, not necessarily one instance per JVM.
  4. Is a singleton bean thread-safe? Not automatically. A shared singleton service should generally be stateless or protect mutable shared state.

13. A microservice receives 10,000 requests simultaneously. How do you handle it?

System designScenario

Model answer

First I would clarify whether 10,000 means requests per second, a sudden burst of 10,000 requests, or 10,000 concurrent open requests. Those are different workloads. I would then use measured capacity and load testing rather than guessing a server/thread count.

  1. Scale horizontally: run multiple stateless service instances behind a load balancer and scale based on CPU, latency, queue depth or request rate.
  2. Protect the service: apply rate limits, request-size limits, authentication controls and admission/concurrency limits.
  3. Manage resources: tune servlet worker threads, database connection pools, HTTP client pools and downstream limits together. More threads than the database can support may make the system slower.
  4. Reduce work: cache suitable read-heavy data, paginate large responses and optimize queries.
  5. Offload asynchronous work: queue long-running tasks and return an accepted/job identifier where the business flow permits.
  6. Observe: monitor p95/p99 latency, throughput, errors, CPU, heap, GC, thread pools, connection pools and downstream health.

For Spring Boot, the servlet container's request handling, database pool (often HikariCP) and outbound HTTP client pools all need coordinated configuration. If using reactive WebFlux, the concurrency model differs; do not mix blocking work onto event-loop threads.

Likely follow-up questions
  1. What is horizontal vs vertical scaling? Horizontal adds instances; vertical increases resources on an instance. Horizontal scaling improves distribution and resilience but requires statelessness or shared state management.
  2. How do you handle a sudden traffic spike? Autoscaling where supported, rate limiting, queues, caching, graceful degradation and capacity headroom.
  3. What if the database is the bottleneck? Optimize queries/indexes, reduce query count, use caching/read replicas where appropriate, and tune pool limits to the database's actual capacity.
  4. How do you avoid overloading downstream services? Apply bulkheads, concurrency limits, timeouts, circuit breakers and controlled queueing.

14. How do you prevent duplicate transactions?

Data consistencyScenario

Model answer

I would not rely only on disabling a submit button in the UI because requests can be retried, duplicated by networks or sent concurrently. I would enforce idempotency at the backend.

  1. Client sends a unique idempotency key for a logical operation.
  2. Server stores the key with operation status and, where useful, a request hash.
  3. A database unique constraint prevents two concurrent requests from claiming the same key.
  4. If the same key is received again, return the previously stored result or current status instead of executing the operation again.
  5. Perform the idempotency record and business write transactionally where possible.

For message consumers, store processed event IDs or use an inbox/deduplication table. Design for at-least-once delivery and make handlers idempotent. For financial or inventory operations, also use appropriate database constraints and atomic updates.

Likely follow-up questions
  1. What is idempotency? Repeating the same logical operation produces the same intended effect as performing it once.
  2. Is HTTP POST idempotent? Not by default. An application can make a POST operation idempotent through an idempotency-key design.
  3. Why is a unique constraint needed if the code checks first? Two concurrent requests can both pass a read-before-write check. The database constraint provides the atomic guarantee.
  4. What if the server crashes after committing but before responding? A retry with the same key finds the committed result and returns it rather than creating another transaction.
  5. What is optimistic locking? A version field or similar check detects concurrent updates and prevents silently overwriting another transaction's change.

15. How do you implement centralized exception handling?

Spring Boot

Model answer

In Spring Boot REST APIs, I use @RestControllerAdvice with @ExceptionHandler methods to map known exceptions to consistent HTTP status codes and error response bodies. This avoids repeating try/catch blocks in every controller.

public record ApiError(String code, String message) {}

@RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<ApiError> validation(
            MethodArgumentNotValidException ex) {
        return ResponseEntity.badRequest().body(
            new ApiError("VALIDATION_ERROR",
                         "One or more fields are invalid"));
    }

    @ExceptionHandler(EntityNotFoundException.class)
    ResponseEntity<ApiError> notFound(EntityNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(
            new ApiError("NOT_FOUND", ex.getMessage()));
    }
}

For unexpected exceptions, log the stack trace internally with a correlation ID and return a generic 500 response. Do not leak SQL, stack traces, internal hostnames or sensitive data.

Likely follow-up questions
  1. @ControllerAdvice vs @RestControllerAdvice? RestControllerAdvice combines ControllerAdvice with response-body semantics, making it convenient for REST error responses.
  2. How do you handle validation errors? Handle MethodArgumentNotValidException and return field-level validation details that are safe and useful.
  3. Should every exception return 500? No. Map known cases to appropriate statuses: 400, 401, 403, 404, 409, 422 where appropriate, 503 for temporary unavailability, and 500 for unexpected server errors.
  4. How do you correlate logs? Generate or propagate a request/trace ID and include it in structured logs and error responses when safe.

16. How do you secure REST APIs using JWT?

Security

Model answer

JWT-based authentication commonly uses a login or identity provider to authenticate a user and issue a signed token. The client sends the token in the Authorization: Bearer header. The resource server verifies the signature and validates claims such as issuer, audience, expiry and not-before time, then uses the authenticated identity and authorities for authorization.

  1. Authenticate the user securely.
  2. Issue a short-lived access token, and use a carefully protected refresh-token flow if required.
  3. Client sends the access token with each protected request.
  4. Server validates signature and claims using a trusted key/issuer configuration.
  5. Authorization rules check roles/scopes and resource ownership.

JWT is signed, not necessarily encrypted. Do not put passwords, secrets or sensitive personal information in claims. Use HTTPS, protect signing keys, choose secure algorithms, validate issuer/audience/expiry, and plan key rotation and revocation strategy.

Likely follow-up questions
  1. Authentication vs authorization? Authentication establishes who the caller is; authorization decides what that identity may do.
  2. Access token vs refresh token? Access tokens are short-lived credentials for APIs. Refresh tokens obtain new access tokens and require stronger storage/rotation protections.
  3. What if a JWT is stolen? A bearer token can be used by whoever possesses it until expiry or revocation controls take effect. Use short expiry, secure transport/storage, rotation and monitoring.
  4. Where should the token be stored? Depends on client architecture. Avoid exposing tokens to XSS; cookie-based designs need CSRF protections. Mobile clients should use platform-secure storage.
  5. How does Spring Security process it? A security filter extracts the bearer token, validates it, creates an Authentication object and places it in the SecurityContext for authorization decisions.

17. What happens internally when Spring Boot starts?

Spring Boot internals

Model answer

The application usually starts through SpringApplication.run(...). Spring Boot prepares the environment and application context, loads configuration and auto-configuration candidates, registers bean definitions, refreshes the context, creates and wires beans, and starts the embedded web server for a web application.

  1. Determine application type and prepare bootstrap environment.
  2. Load properties/YAML, profiles, environment variables and command-line properties.
  3. Create the appropriate ApplicationContext.
  4. Register component and configuration bean definitions.
  5. Apply auto-configuration based on classpath, properties and existing beans.
  6. Refresh the context: instantiate non-lazy singletons, resolve dependencies and run lifecycle callbacks.
  7. Start embedded server and publish application-ready lifecycle events.

Example entry point

@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

@SpringBootApplication combines configuration, component scanning and auto-configuration enablement. Auto-configuration is conditional; it backs off when relevant user-defined beans or conditions are present.

Likely follow-up questions
  1. What is auto-configuration? Configuration selected using conditions such as classpath presence, properties and existing beans, reducing manual setup.
  2. What is @ConditionalOnClass? A configuration or bean is considered only when a specified class is present on the classpath.
  3. What is @ConditionalOnProperty? A bean/configuration is enabled or disabled based on an application property.
  4. What does component scanning do? Finds eligible stereotype-annotated classes in configured packages and registers them as bean definitions.
  5. What is the difference between bean definition and bean instance? A definition describes how to create/configure a bean; the instance is the actual object created by the container.

18. How does Spring manage singleton beans in a multithreaded environment?

Spring internals

Model answer

Spring's default singleton scope creates one bean instance per bean definition per application context. Multiple request threads may invoke methods on that same object concurrently. Spring manages bean creation and lifecycle, but it does not automatically make mutable fields thread-safe.

For service beans, prefer stateless design: keep request-specific values in local variables and pass them through method parameters. Avoid storing a user's request data in instance fields. If shared mutable state is truly required, use appropriate concurrency controls or a thread-safe data structure, while considering whether the state belongs in a database or distributed cache instead.

Unsafe example

@Service
class UnsafeService {
    private String currentUser; // shared mutable field

    public void process(String user) {
        currentUser = user;
        // Another request can overwrite this value.
    }
}
Likely follow-up questions
  1. Does singleton mean one instance per JVM? No. It is one instance per bean definition per Spring application context. Multiple contexts or application instances have their own objects.
  2. Are local variables thread-safe? Each invocation has its own stack frame, so local variables are not shared in the same way. Objects referenced by them can still be shared.
  3. Can prototype beans be injected into singleton beans? A prototype injected directly is generally resolved at singleton creation time. Use a provider/object factory or scoped proxy when a fresh instance is needed per use.
  4. What is ThreadLocal? A value associated with a thread. It needs careful cleanup in thread pools and should not be used to pass state across asynchronous thread changes.

19. How would you troubleshoot a memory leak?

JVMTroubleshooting

Model answer

I would first confirm that memory usage grows over time and does not return to a stable level after garbage collection. I would distinguish Java heap growth from native memory, direct buffers, metaspace, thread stacks or container-level memory. Then I would collect evidence rather than increasing heap immediately.

  1. Review heap usage, GC logs, allocation rate, container memory and restart history.
  2. Capture a heap dump when safe, preferably near the point of high usage.
  3. Analyze the dominator tree and retained sizes in a tool such as Eclipse MAT or a supported profiler.
  4. Look for unbounded collections, static references, caches without eviction, listeners not removed, ThreadLocal values not cleared and objects retained by long-lived references.
  5. Fix the ownership/lifecycle issue, add limits or eviction, and reproduce under load to confirm memory stabilizes.

Useful tools include jcmd, Java Flight Recorder, GC logs and heap-dump analyzers. In production, account for the impact of generating a dump and protect the dump because it may contain sensitive data.

Likely follow-up questions
  1. OutOfMemoryError vs memory leak? OOM is a failure condition; a leak is one possible cause. OOM can also result from genuinely insufficient capacity, large allocations or native-memory exhaustion.
  2. What is a heap dump? A snapshot of heap objects and references, useful for identifying retained objects and memory ownership paths.
  3. What is a memory leak in Java if GC exists? Objects remain reachable through references even though the application no longer needs them, so GC cannot reclaim them.
  4. What is GC? Garbage collection reclaims heap memory occupied by objects that are no longer reachable, subject to JVM implementation and reachability rules.

20. How do you deploy a new microservice version without downtime?

DeploymentScenario

Model answer

I would use a deployment strategy that keeps healthy instances serving traffic while the new version is started and verified. A rolling deployment replaces instances gradually; blue-green deployment runs old and new environments side by side and switches traffic after validation. Canary deployment sends a small percentage of traffic to the new version before increasing it.

  1. Build an immutable, versioned artifact and run automated unit, integration and security tests.
  2. Deploy new instances without immediately sending production traffic.
  3. Use readiness checks to ensure an instance is ready to serve requests; liveness checks should detect unrecoverable process failure.
  4. Gradually route traffic to new instances and monitor error rate, latency, saturation and business metrics.
  5. Drain old instances gracefully so in-flight requests can complete.
  6. Keep rollback capability and ensure database changes are backward-compatible during the transition.

Database migrations are often the hardest part. Use an expand-and-contract approach: add compatible schema first, deploy code that supports both states, migrate data, then remove old schema only after old code is gone.

Likely follow-up questions
  1. Rolling vs blue-green vs canary? Rolling replaces instances gradually; blue-green switches between two environments; canary gradually exposes a subset of users/traffic to the new version.
  2. Liveness vs readiness probe? Liveness asks whether the process should be restarted. Readiness asks whether it should receive traffic.
  3. How do you roll back a database change? Prefer backward-compatible migrations and forward-fix/compensating migration plans. A destructive schema change may not be safely reversible.
  4. What is graceful shutdown? Stop accepting new work, allow in-flight requests to finish within a configured period, then terminate cleanly.
  5. How do you know deployment is healthy? Compare key service-level indicators and business metrics against baseline, watch logs/traces and validate critical user journeys.

🧩 Microservices Architecture — Quiz Application

A complete walkthrough of how Quiz-Service & Question-Service communicate via OpenFeign

1   High-Level Overview

This project is a Spring Boot microservices quiz application composed of four independently deployable services, each with its own responsibility:

📋

Service Registry

Port 8761 · Eureka Server

Central registry where all services register themselves. Others discover each other through it.

🌐

API Gateway

Port 8765 · Spring Cloud Gateway

Single entry point for all client requests. Routes traffic to the correct microservice via service discovery.

❓

Question Service

Default Port 8080 · DB: questiondb

Manages questions — CRUD, random selection by category, fetching by IDs, and scoring.

🏆

Quiz Service

Port 8090 · DB: quizdb

Creates quizzes, stores question IDs, and delegates question-related work to the Question Service via Feign Client.

3   Service Registry (Eureka Server)

The Service Registry runs a Netflix Eureka server. Every other service registers itself here on startup. This enables service discovery — services locate each other by name rather than hard-coded URLs. 

// ServiceRegistryApplication.java
@SpringBootApplication
@EnableEurekaServer               // ← Starts Eureka Server
public class ServiceRegistryApplication { ... }

# application.properties
server.port=8761
eureka.client.register-with-eureka=false   // it IS the registry, so don't self-register
eureka.client.fetch-registry=false

4   API Gateway

The gateway is the single entry point for external clients. It uses Spring Cloud Gateway with Discovery Locator enabled, so routes are automatically created from the Eureka registry. 

# application.properties
server.port=8765
spring.cloud.gateway.discovery.locator.enabled=true
spring.cloud.gateway.discovery.locator.lower-case-service-id=true

Example: A request to http://localhost:8765/quiz-service/quiz/create is automatically routed to the quiz-service instance discovered via Eureka.

// Compares user responses with rightAnswer
public ResponseEntity<Integer> getScore(List<Response> responses) {
    int right = 0;
    for (Response r : responses) {
        Question q = questionDao.findById(r.getId()).get();
        if (r.getResponse().equals(q.getRightAnswer())) right++;
    }
    return new ResponseEntity<>(right, HttpStatus.OK);
}

7   The Feign Client — Connecting the Two Services

💡 What is OpenFeign?

OpenFeign is a declarative HTTP client from Spring Cloud. Instead of writing RestTemplate or WebClient boilerplate, you simply declare a Java interface that mirrors the target service's REST endpoints. Spring auto-generates the HTTP implementation at runtime.

7.1   Enable Feign in Quiz Service

// QuizServiceApplication.java
@SpringBootApplication
@EnableFeignClients       // ← Scans for @FeignClient interfaces
public class QuizServiceApplication { ... }

7.2   The Feign Interface — QuizInterface.java

@FeignClient("QUESTION-SERVICE")   // ← Eureka service name of the target
public interface QuizInterface {

    // Maps to GET /question/generate on Question-Service
    @GetMapping("question/generate")
    ResponseEntity<List<Integer>> getQuestionsForQuiz(
            @RequestParam String categoryName,
            @RequestParam Integer numQuestions);

    // Maps to POST /question/getQuestions on Question-Service
    @PostMapping("question/getQuestions")
    ResponseEntity<List<QuestionWrapper>> getQuestionsFromId(
            @RequestBody List<Integer> questionIds);

    // Maps to POST /question/getScore on Question-Service
    @PostMapping("question/getScore")
    ResponseEntity<Integer> getScore(
            @RequestBody List<Response> responses);
}

🔑 How the magic works

  • @FeignClient("QUESTION-SERVICE") tells Feign to look up QUESTION-SERVICE in the Eureka registry to discover its host & port.
  • Each method's @GetMapping / @PostMapping mirrors the exact endpoint exposed by the Question Service controller.
  • Spring creates a proxy at runtime — when QuizService calls quizInterface.getQuestionsForQuiz(...), Feign makes an actual HTTP GET to http://QUESTION-SERVICE/question/generate?categoryName=...&numQuestions=....
  • Eureka resolves QUESTION-SERVICE to the real IP:port (e.g. localhost:8080) and supports client-side load balancing if multiple instances are running.

7.3   Endpoint Mapping (Feign ↔ Question Controller)

Feign Method (Quiz Service) → Controller Method (Question Service) HTTP
getQuestionsForQuiz(category, num) → QuestionController.getQuestionsForQuiz() GET /question/generate
getQuestionsFromId(ids) → QuestionController.getQuestionsFromId() POST /question/getQuestions
getScore(responses) → QuestionController.getScore() POST /question/getScore

8   End-to-End Request Flows

Flow A — Create a Quiz (POST /quiz/create)

1
Client → API Gateway sends POST /quiz-service/quiz/create with body: 
{ "categoryName": "Java", "numQuestions": 5, "title": "Java Basics" }
2
Gateway → Quiz Service routes to /quiz/create. QuizController.createQuiz() calls QuizService.createQuiz().
3
Quiz Service → Question Service (Feign)
quizInterface.getQuestionsForQuiz("Java", 5)
Feign sends GET http://QUESTION-SERVICE/question/generate?categoryName=Java&numQuestions=5
4
Question Service runs findRandomQuestionsByCategory("Java", 5) → returns 5 random question IDs, e.g. [3, 7, 12, 18, 21].
5
Quiz Service receives the IDs, creates a Quiz entity (title + IDs), saves it to quizdb, and returns 201 Created "Success".

Flow B — Get Quiz Questions (POST /quiz/get/{id})

1
Client → Quiz Service sends POST /quiz/get/1.
2
Quiz Service loads the Quiz from DB → gets questionIds = [3, 7, 12, 18, 21].
3
Quiz Service → Question Service (Feign)
quizInterface.getQuestionsFromId([3, 7, 12, 18, 21])
Feign sends POST http://QUESTION-SERVICE/question/getQuestions with the ID list as body.
4
Question Service fetches each question, maps it to QuestionWrapper (which excludes rightAnswer), and returns the list.
5
Quiz Service forwards the list of QuestionWrapper objects back to the client.

Flow C — Submit Quiz & Get Score (POST /quiz/submit/{id})

1
Client → Quiz Service sends POST /quiz/submit/1 with body: 
[
  { "id": 3,  "response": "Option A" },
  { "id": 7,  "response": "Option C" },
  { "id": 12, "response": "Option B" },
  ...
]
2
Quiz Service → Question Service (Feign)
quizInterface.getScore(responses)
Feign sends POST http://QUESTION-SERVICE/question/getScore with the responses.
3
Question Service compares each response with the rightAnswer stored in DB and returns the count of correct answers (e.g. 3).
4
Quiz Service returns the score to the client.

9   Database Separation

Each service has its own PostgreSQL database, following the microservice pattern of database-per-service:

questiondb

Stores question table — id, title, options, rightAnswer, difficulty, category.

quizdb

Stores quiz table (id, title) + quiz_question_ids join table (quiz_id → question_id).

11   Key Takeaways

🔗

Feign = Declarative HTTP

No manual RestTemplate code. Just define an interface with Spring MVC annotations and Feign does the rest.

🔍

Eureka = Discovery

@FeignClient("QUESTION-SERVICE") resolves the target host:port dynamically from the registry.

⚖️

Load Balancing

If multiple Question Service instances are registered, Feign + Spring Cloud LoadBalancer distribute calls automatically.

🚪

Gateway = Single Entry

Clients only need to know the gateway URL. Internal routing is handled by service discovery.

🗄️

Database per Service

Each service owns its data. The Quiz Service stores only question IDs, not the questions themselves.

🛡️

QuestionWrapper = Security

The wrapper DTO strips rightAnswer so clients never see correct answers when fetching questions.

12   Q & A — Concepts Deep Dive

Common questions that came up while studying this codebase, with detailed answers.

Q1: What does "orchestrator" mean in this context?

In this microservices project, "orchestrator" refers to the Quiz Service's role in coordinating work across multiple services without doing the actual data processing itself.

The Quiz Service:

  • Receives the client's request (e.g., "create a quiz with 5 Java questions")
  • Delegates the actual work to the Question Service via Feign (e.g., "give me 5 random Java question IDs")
  • Combines / stores the results (saves the quiz with those IDs in its own DB)
  • Returns the final response to the client

It doesn't own or process question data — it coordinates (orchestrates) the flow between the client and the Question Service, like a conductor directing an orchestra. The Quiz Service knows what needs to happen and who should do it, but the heavy lifting (querying questions, checking answers) is done by the Question Service. 

// Example — "Create Quiz" flow:

Client  →  Quiz Service (orchestrator)  →  Question Service (data owner)
                │                                      │
                │  "I need 5 Java question IDs"        │
                │ ──────── Feign call ────────────────► │
                │                                      │  (queries DB, picks random IDs)
                │  ◄───────── [3,7,12,18,21] ────────── │
                │
                │  saves Quiz(title, [3,7,12,18,21]) to quizdb
                │  returns "Success" to client

The opposite pattern would be choreography, where each service reacts to events independently with no central coordinator.

Q2: What is Environment and how can I use it?

org.springframework.core.env.Environment is a Spring interface that gives you runtime access to application properties, system properties, and environment variables.

How it's used in the code

@Autowired
Environment environment;

It's injected into QuestionController, and used here:

@PostMapping("getQuestions")
public ResponseEntity<List<QuestionWrapper>> getQuestionsFromId(@RequestBody List<Integer> questionIds){
    System.out.println(environment.getProperty("local.server.port"));  // ← HERE
    return questionService.getQuestionsFromId(questionIds);
}

It prints the port number the service is currently running on. This is useful when you run multiple instances of Question Service (for load balancing) — you can see in the console which instance handled the Feign request.

What else you can do with it

// Read any property from application.properties
environment.getProperty("spring.datasource.url");       // → "jdbc:postgresql://localhost:5432/questiondb"
environment.getProperty("spring.application.name");      // → "question-service"

// Read with a default fallback
environment.getProperty("some.missing.key", "default");  // → "default"

// System / OS environment variables
environment.getProperty("JAVA_HOME");                    // → "C:\Program Files\Java\jdk-17"
environment.getProperty("PATH");

// Check active profiles (dev, prod, etc.)
environment.getActiveProfiles();                         // → String[] e.g. ["dev"]

// Check if a property exists
environment.containsProperty("server.port");             // → true

Why it matters here specifically: When Quiz Service calls getQuestionsFromId via Feign, and you have 2+ instances of Question Service registered in Eureka (e.g., on ports 8080 and 8081), the environment.getProperty("local.server.port") log tells you which instance Eureka's load balancer routed the request to — useful for verifying load balancing is working.

Q3: How does load balancing work? What code in the project enables it?

There is no explicit load balancing code you wrote — it's all automatic. Three pieces of the project combine to make it work:

Piece 1 — The dependency (quiz-service/pom.xml)

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-openfeign</artifactId>
</dependency>

This dependency automatically includes spring-cloud-loadbalancer inside it. You don't see a separate load balancer dependency because Feign bundles it. This provides client-side load balancing (Round Robin by default).

Piece 2 — The Feign interface (QuizInterface.java)

@FeignClient("QUESTION-SERVICE")   // ← service NAME, not a URL

The key is "QUESTION-SERVICE" — this is not a hardcoded URL like http://localhost:8080. It's the Eureka service name. When Feign sees a name instead of a URL, it:

  • Asks Eureka: "Who are all the instances of QUESTION-SERVICE?"
  • Eureka returns a list (e.g., localhost:8080, localhost:8081)
  • The built-in Spring Cloud LoadBalancer picks one using Round Robin

Piece 3 — The debug/proof line (QuestionController.java)

System.out.println(environment.getProperty("local.server.port"));  // ← verification

If you run 2 instances of Question Service and make multiple Feign calls, the console logs alternate between the two ports — proving Round Robin is active.

The complete chain visualised

Quiz Service calls quizInterface.getQuestionsFromId(ids)
        │
        ▼
  Feign sees @FeignClient("QUESTION-SERVICE")
        │
        ▼
  Asks Eureka: "Give me all QUESTION-SERVICE instances"
        │
        ▼

Q4: What is Round Robin?

Round Robin is the simplest load balancing strategy — it distributes requests equally, one by one, in order across all available instances, then loops back.

How it works with 3 instances

Say you run 3 instances of Question Service registered in Eureka:

Instance A → localhost:8080
Instance B → localhost:8081
Instance C → localhost:8082

When Quiz Service makes Feign calls, the load balancer picks them in a rotating cycle:

Request 1  →  Instance A (8080)
Request 2  →  Instance B (8081)
Request 3  →  Instance C (8082)
Request 4  →  Instance A (8080)   ← back to start
Request 5  →  Instance B (8081)
Request 6  →  Instance C (8082)
...repeats forever

It's like dealing cards — each instance gets a turn, then it goes around again.

What you'd see in the console

That environment.getProperty("local.server.port") line would print:

Instance A console:  8080       ← Request 1
Instance B console:  8081       ← Request 2
Instance C console:  8082       ← Request 3
Instance A console:  8080       ← Request 4 (round robin looped)

Comparison with other strategies

FeatureRound Robin
Logicnext = (current + 1) % totalInstances
Fair?Yes — every instance gets equal traffic
Smart?No — doesn't consider if one instance is slow or overloaded
Default?Yes — Spring Cloud LoadBalancer uses this by default, which is what this project gets automatically via the Feign dependency

Other strategies (not used here, but exist)

  • Random — picks a random instance each time
  • Weighted — some instances get more traffic than others
  • Least Connections — picks the instance with fewest active requests (smarter but more complex)

This project uses Round Robin because nothing else was configured — it's the default that comes bundled with spring-cloud-starter-openfeign, and for most use cases it works well enough.

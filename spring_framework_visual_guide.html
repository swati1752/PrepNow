How the pieces fit together

Spring is an IoC container plus a broad set of infrastructure features. You describe objects (beans) and their relationships; Spring creates and wires them, applies lifecycle callbacks and infrastructure, and lets the application react to configuration and events.

Keep the levels distinct: Dependency Injection (DI) is a design technique; the Spring Framework is the library/platform; Spring Boot simplifies setup and auto-configuration; AOP is a programming approach; proxies are one mechanism Spring AOP commonly uses.
01 · resource management

RAII — Resource Acquisition Is Initialization

RAII is a resource-management idiom most associated with C++. It ties a resource's lifetime to an object's lifetime: acquire the resource when the object is initialized, and release it when the object is destroyed. This helps prevent leaks when execution exits early or throws an exception.

Typical resourcesFiles, locks, sockets, memory, database handles.
Core ideaMake ownership and cleanup predictable rather than relying on every caller to remember cleanup.

Visualization: resource lifetime

How this relates to Java and Spring: Java does not have C++ destructors/RAII in exactly the same form. Use try-with-resources for objects implementing AutoCloseable. Spring beans can use lifecycle callbacks such as @PreDestroy or DisposableBean to clean up resources when the application context shuts down.

// Java: deterministic cleanup with try-with-resources
try (var reader = Files.newBufferedReader(Path.of("input.txt"))) {
    System.out.println(reader.readLine());
} // reader.close() is called even if an exception occurs
Important distinction: A Spring bean's @PreDestroy is not a substitute for try-with-resources for short-lived local resources. It is generally for resources owned by a long-lived bean and cleaned up when that bean is destroyed.
02 · object wiring

DI — Dependency Injection

A class has a dependency when it needs another object to do its work. With DI, the class does not construct that dependency itself; an external assembler (often Spring's container) supplies it. This reduces coupling and makes code easier to test, replace, and configure.

Before DI
Service creates its own repository
→
With DI
Container supplies repository
public interface PaymentRepository {
    void save(String paymentId);
}

@Service
public class PaymentService {
    private final PaymentRepository repository;

    // Constructor injection
    public PaymentService(PaymentRepository repository) {
        this.repository = repository;
    }

    public void pay(String id) {
        repository.save(id);
    }
}

Common injection styles

StyleUseNotes
ConstructorRequired dependenciesUsually preferred; supports immutability and easy unit tests.
SetterOptional or reconfigurable dependenciesCan leave an object partially configured if misused.
FieldShort examples / legacy codeConvenient, but hides dependencies and makes plain unit testing harder.

DI vs IoC: Inversion of Control is the broader principle of handing control over object creation/wiring to a framework. DI is one way to achieve IoC.

A portable service abstraction gives your application a consistent Spring-facing API over infrastructure that may differ between environments or providers. The application can depend on a stable contract rather than embedding provider-specific code everywhere.

04 · cross-cutting behavior

AOP — Aspect-Oriented Programming

AOP separates concerns that cut across many classes—such as transactions, authorization, metrics, or logging—from the main business logic. In Spring AOP, advice is commonly applied through proxies around Spring-managed beans.

AspectA module that groups a cross-cutting concern.
AdviceThe action to run, e.g. before or after a method.
PointcutA rule selecting join points/method executions.
ProxyThe intercepting object that allows advice to run.
@Aspect
@Component
public class TimingAspect {
    @Around("execution(* com.example.service..*(..))")
    public Object time(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        try {
            return joinPoint.proceed(); // call the target method
        } finally {
            System.out.println("Elapsed ns: " +
                (System.nanoTime() - start));
        }
    }
}

→
Target method
→
Advice completes
Proxy caveat: in default proxy-based Spring AOP, a method calling another method on the same object (self-invocation) bypasses the proxy. Also, only calls that pass through the proxy are intercepted. AspectJ weaving has different capabilities.
05 · platform

Spring Framework

The Spring Framework is a modular Java framework. Its core container manages objects and their dependencies; other modules provide web MVC, data access integration, transactions, testing support, messaging, and AOP integration.

Core containerIoC, DI, bean definitions, lifecycle.
AOPCross-cutting behavior such as transactions.
Data accessTransaction APIs and integrations with persistence technologies.
WebSpring MVC and related web infrastructure.

Think of Spring Framework as the underlying toolkit. It does not force every application to use every module.

06 · finding beans

Component scanning

Component scanning searches configured packages for classes marked with stereotype annotations such as @Component, @Service, @Repository, and @Controller, then registers bean definitions for them.

@SpringBootApplication
public class StoreApplication {
    public static void main(String[] args) {
        SpringApplication.run(StoreApplication.class, args);
    }
}

// @SpringBootApplication includes @ComponentScan
@Service
public class InventoryService { }

Default package: @SpringBootApplication normally scans its package and subpackages. Put the application class near the root of your code packages, or configure @ComponentScan explicitly.

Component scanning discovers candidates; it does not mean every class in the project becomes a bean. Ordinary classes without registration or a bean-definition mechanism are not automatically managed.
07 · creation to shutdown

Spring bean lifecycle

A bean is an object managed by the Spring container. The exact lifecycle varies with bean scope and configuration, but a singleton bean commonly follows the stages below.

1. Instantiate
Spring creates the bean instance, commonly using a constructor or factory method. Dependency properties have not necessarily been injected yet.
Initialization order (simplified): injection and aware callbacks → BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct / InitializingBean.afterPropertiesSet() / custom init method → BeanPostProcessor.postProcessAfterInitialization → bean ready. The exact callback ordering has framework-defined details; custom processors may wrap or replace the bean.

Lifecycle callbacks at a glance

HookWhen / purpose
@PostConstructRun after dependency injection during initialization; useful for validation or preparing state.
InitializingBean.afterPropertiesSet()Spring-specific initialization callback after properties are set.
Custom init methodConfigured with @Bean(initMethod = "...") or bean-definition settings.
@PreDestroyCleanup callback before a managed bean is destroyed.
DisposableBean.destroy()Spring-specific destruction callback.
Custom destroy methodConfigured with @Bean(destroyMethod = "...") or bean-definition settings.
@Component
public class ReportCache {
    @PostConstruct
    void initialize() {
        // Validate configuration / prepare cache
    }

    @PreDestroy
    void cleanup() {
        // Release bean-owned resources
    }
}
The container generally manages destruction callbacks for singleton beans when the context shuts down. Prototype-scoped beans are created by Spring, but Spring does not manage their full destruction lifecycle in the same way—callers are responsible for cleanup.
08 · container extension points

BeanFactoryPostProcessor vs BeanPostProcessor

Both are extension points, but they operate at different levels and times.

BeanFactoryPostProcessorChanges bean definitions / metadata before regular beans are instantiated. Example: altering property values or definitions.
BeanPostProcessorWorks with actual bean instances around initialization. Can inspect, modify, or wrap a bean with a proxy.
Load bean definitions
→
BeanFactoryPostProcessor
definition metadata
→
Create bean instances
→
BeanPostProcessor
bean objects
@Component
public class ExamplePostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessAfterInitialization(
            Object bean, String beanName) {
        // Inspect or wrap the initialized bean.
        return bean;
    }
}

Spring uses bean post-processors internally for features such as annotation processing and proxy-based behavior. For example, infrastructure processors help recognize lifecycle annotations and create AOP proxies.

Be careful: beans created very early to configure the container may not receive every normal post-processing step. Keep post-processors lightweight and avoid depending on ordinary application beans unless you understand initialization ordering.
09 · opinionated setup

Spring Boot and BeanPostProcessor

Spring Boot is built on the Spring Framework. It simplifies application setup with auto-configuration, starter dependencies, externalized configuration, and convenient application startup. BeanPostProcessor itself belongs to the Spring Framework—not a Boot-only feature.

Spring Boot app
→
Auto-configuration + component scan
→
Spring ApplicationContext
→
Framework bean lifecycle + processors

Boot can contribute configuration and infrastructure beans that rely on the Framework's bean lifecycle and post-processing machinery. You can also register your own processor when necessary.

@Configuration
public class ProcessorConfiguration {
    @Bean
    static BeanFactoryPostProcessor definitionCustomizer() {
        return beanFactory -> {
            // Customize bean definitions here, if needed.
        };
    }
}
A BeanFactoryPostProcessor factory method is commonly declared static so Spring can create it without prematurely instantiating the configuration class. Use this extension point only when regular configuration mechanisms are insufficient.
10 · externalized settings

Environment, PropertySource, @Value and @ConfigurationProperties

Spring's Environment provides access to active profiles and properties. Property values come from ordered PropertySource objects, such as configuration files, environment variables, system properties, and command-line arguments. The winning value depends on property-source precedence.

Three common tools

ToolBest forExample

@ValueA small number of individual values or expressions.@Value("${app.timeout:5s}")
@ConfigurationPropertiesBind a related group of settings into a typed object.app.client.timeout → field timeout
// application.yml
app:
  client:
    base-url: https://api.example.com
    timeout: 3s
    max-retries: 4

@ConfigurationProperties(prefix = "app.client")
public class ClientProperties {
    private URI baseUrl;
    private Duration timeout = Duration.ofSeconds(3);
    private int maxRetries = 3;
    // getters and setters, or use a supported constructor-binding style
}

Register the properties class with @ConfigurationPropertiesScan or @EnableConfigurationProperties(ClientProperties.class) when it is not otherwise registered.

What is EnvironmentPostProcessor?

EnvironmentPostProcessor is a Spring Boot extension point that can customize the Environment before the application context is refreshed and beans are created. It is useful when a custom property source must be added early. It is not the same as BeanFactoryPostProcessor: one customizes the Environment; the other customizes bean definitions.

Avoid putting secrets directly into source-controlled config files. Use an appropriate secret store or deployment-time secret injection, and confirm the active profiles and property precedence when a value looks unexpected.
11 · communication between components

Spring application events

Events let one component announce that something happened without directly calling every interested listener. A publisher publishes an event; one or more listeners react to it. This is useful for decoupling, but it does not automatically make work asynchronous or durable.

Business service
→
Publish event
→
Application event multicaster
→
One or more listeners
public record OrderPlaced(String orderId) {}

@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public OrderService(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void place(String id) {
        // Persist order first...
        publisher.publishEvent(new OrderPlaced(id));
    }
}

@Component
public class OrderNotificationListener {
    @EventListener
    public void onOrderPlaced(OrderPlaced event) {
        System.out.println("Notify for " + event.orderId());
    }
}

Events worth knowing

Event / mechanismMeaning
ContextRefreshedEventAn application context was initialized or refreshed.
ContextStartedEventA context received a start signal (less common in typical Boot apps).
ContextStoppedEventA context received a stop signal.
ContextClosedEventThe context is closing.
ApplicationStartedEventSpring Boot has started the application context; runners have not yet completed.
ApplicationReadyEventSpring Boot indicates the application is ready to service requests.
ApplicationFailedEventSpring Boot startup failed.
@EventListenerAnnotation-based listener for application events, including custom event types.

Use @TransactionalEventListener when handling an event in relation to a transaction phase (commonly after commit). If a notification must never be lost, consider a durable messaging/outbox design rather than relying only on an in-memory application event.

By default, Spring application event listeners commonly execute synchronously in the publishing thread. Async execution requires configuration such as @Async with async support enabled, and it introduces its own error-handling and ordering considerations.

Recap & interview checks

RAII → resource lifetimeDI → supply dependenciesPortable abstraction → stable APIAOP → cross-cutting concernComponent scan → discover beansLifecycle → initialize / destroyBFPP → bean definitionsBPP → bean instancesEnvironment → properties + profilesEvents → publish / listen
Why prefer constructor injection?

It makes required dependencies explicit, allows fields to be final, and makes unit tests straightforward without needing the Spring container.

What is the key difference between BeanFactoryPostProcessor and BeanPostProcessor?

The former works on bean-definition metadata before ordinary beans are instantiated; the latter works on bean instances around initialization.

Does @PostConstruct run before dependency injection?

No. It runs after dependencies have been injected, during bean initialization.

Is Spring Boot's BeanPostProcessor different from Spring Framework's?

No. BeanPostProcessor is a Spring Framework interface. Spring Boot builds on the Framework and may register processors or configuration that uses it.

Are Spring application events always asynchronous?

No. By default, listeners commonly run synchronously unless async handling is configured.

Why might @Transactional not work on a self-invoked method?

In proxy-based AOP, an internal call on this bypasses the proxy, so the transactional interceptor is not invoked for that call.

Learning note: callback ordering and auto-configuration details can vary by Spring version and setup. Use the reference documentation for the exact version used in your project.

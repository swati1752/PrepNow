Core Java & JVM Internals
  • How does the HashMap work internally in Java 8+?
    • Answer: It uses an array of Nodes (buckets). Key hashCode() determines the index via (n - 1) & hash. Collisions are handled using a Singly Linked List. In Java 8+, if a bucket's node count reaches 8 (TREEIFY_THRESHOLD) and total map capacity is ≥ 64, the bucket converts from a Linked List to a Red-Black Tree ($O(n) \rightarrow O(\log n)$ lookup). If nodes drop below 6 (UNTREEIFY_THRESHOLD), it converts back.
  • Difference between CompletableFuture and traditional Future?
    • Answer: Future requires blocking (get()) or polling to check completion. CompletableFuture supports non-blocking reactive chains (thenApply, thenCompose, exceptionally), manual completion, and combining multiple async operations (allOf, anyOf).
Spring Boot & Architecture
  • How does Spring Boot Auto-Configuration work?
    • Answer: Enabled via @EnableAutoConfiguration (part of @SpringBootApplication). It checks META-INF/spring.factories (or AutoConfiguration.imports in Spring Boot 3) to load configuration classes based on classpath dependencies using conditional annotations like @ConditionalOnClass and @ConditionalOnProperty.
  • Bean Scopes in Spring Boot:
    • Singleton (Default): Single instance per Spring IoC container.
    • Prototype: New instance every time a bean is requested.
    • Request: One instance per HTTP request (Web context).
    • Session: One instance per HTTP session (Web context).
  • How to fix a circular dependency in Spring?
    • Answer: Avoid component coupling by refactoring code (e.g., using a third helper service). If refactoring isn't immediate, use @Lazy on one of the injected constructor dependencies.
Microservices, Transactions & Database
  • How do @Transactional annotations work, and when do they fail?
    • Answer: Uses Spring AOP proxies around the method to manage transaction lifecycle (begin, commit, rollback).
    • Failure cases:
      1. Self-invocation: Calling a @Transactional method within the same class bypasses the Spring proxy.
      2. Uncaught Checked Exceptions: By default, it rolls back only on RuntimeException and Error. Fix using @Transactional(rollbackFor = Exception.class).
      3. Non-public methods: Spring AOP ignores private/protected methods.

Difference between Abstraction and Encapsulation.
Assistant
Abstraction hides internal complexity and exposes only essential functionality (focuses on what an object does), while Encapsulation binds data and methods into a single unit and restricts direct access (focuses on how data is hidden and protected).
Key Differences
FeatureAbstractionEncapsulation
Core GoalHide implementation details / reduce complexityHide data / protect object state from unauthorized access
FocusWhat the system doesHow the data is bundled and secured
ImplementationAchieved via Interfaces and Abstract ClassesAchieved via Access Modifiers (private, protected, public) and Getters/Setters
Design LevelOuter design level (Interface level)Inner implementation level (Data level)
Real-World AnalogyDriving a car: You press the accelerator, but don't need to know engine combustion details.Car dashboard: Engine components are sealed under the hood; you interact safely through pedals and knobs.
Java Code Example 
// ABSTRACTION: Interface defines WHAT to do without revealing HOW
interface BankAccount {
    void deposit(double amount);
    void withdraw(double amount);
}

// ENCAPSULATION: Class bundles data + methods and hides inner state
public class SavingsAccount implements BankAccount {
    // Hidden data (private variable)
    private double balance;

    public SavingsAccount(double initialBalance) {
        this.balance = initialBalance;
    }

    // Encapsulated access via validated method
    @Override
    public void deposit(double amount) {
        if (amount > 0) {
            this.balance += amount;
        }
    }

    @Override
    public void withdraw(double amount) {
        if (amount > 0 && amount <= balance) {
            this.balance -= amount;
        }
    }

    // Controlled getter
    public double getBalance() {
        return balance;
    }
}

Encapsulation is an implementation-level technique that hides sensitive class fields using private access modifiers and exposes controlled access via public methods, preventing unauthorized mutations."

Explain SOLID principles with examples.
Assistant
SOLID is an acronym for five object-oriented design principles that help engineers build maintainable, scalable, and loosely coupled applications.

1. Single Responsibility Principle (SRP)

Definition: A class should have one, and only one, reason to change.
  • Violation: A single class managing user profile logic, database persistence, and sending emails.
  • Solution: Separate concerns into dedicated classes.
// Good: Each class has a single responsibility
public class Invoice {
    public double calculateTotal() { return 100.0; }
}

public class InvoiceRepository {
    public void saveToDatabase(Invoice invoice) { /* DB operations */ }
}

public class EmailService {
    public void sendReceipt(Invoice invoice) { /* Mail logic */ }
}

2. Open/Closed Principle (OCP)

Definition: Software entities should be open for extension, but closed for modification.
  • Violation: Using if-else or switch blocks inside a payment processor to check payment types. Adding a new payment method requires modifying the existing class.
  • Solution: Use polymorphism via interfaces or abstract classes.
public interface PaymentMethod {
    void process(double amount);
}

public class CreditCardPayment implements PaymentMethod {
    public void process(double amount) { /* Process CC */ }
}

public class UPIPayment implements PaymentMethod {
    public void process(double amount) { /* Process UPI */ }
}

public class PaymentProcessor {
    public void executePayment(PaymentMethod method, double amount) {
        method.process(amount); // Extensible without changing this class
    }
}

3. Liskov Substitution Principle (LSP)

Definition: Derived classes must be substitutable for their base classes without breaking the correctness of the program.
  • Violation: A Square subclass inheriting from a Rectangle base class altering width unexpectedly. Or a Bird class with a fly() method, where subclass Ostrich throws UnsupportedOperationException.
  • Solution: Restructure hierarchy using interfaces that reflect actual capabilities.
public interface Bird {}

public interface FlyingBird extends Bird {
    void fly();
}

public class Sparrow implements FlyingBird {
    public void fly() { System.out.println("Flying"); }
}

public class Ostrich implements Bird {
    // Doesn't implement FlyingBird, avoiding invalid overrides
}

4. Interface Segregation Principle (ISP)

Definition: Clients should not be forced to depend on interfaces they do not use.
  • Violation: A single "fat" Worker interface containing work(), eat(), and sleep() forcing a RobotWorker to implement unused methods.
  • Solution: Break large interfaces into smaller, specialized ones.
public interface Workable {
    void work();
}

public interface Feedable {
    void eat();
}

public class RobotWorker implements Workable {
    public void work() { System.out.println("Robot working"); }
}

public class HumanWorker implements Workable, Feedable {
    public void work() { System.out.println("Human working"); }
    public void eat() { System.out.println("Human eating"); }
}

5. Dependency Inversion Principle (DIP)

Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions.
  • Violation: Instantiating concrete dependencies directly using new inside a high-level component.
  • Solution: Depend on an interface abstraction and inject the dependency.
public interface NotificationService {
    void sendNotification(String message);
}

public class EmailNotification implements NotificationService {
    public void sendNotification(String message) { /* Send Email */ }
}

public class OrderProcessor {
    private final NotificationService notificationService;

    public OrderProcessor(NotificationService notificationService) {
        this.notificationService = notificationService;
    }

    public void completeOrder() {
        notificationService.sendNotification("Order completed!");
    }
}

can you explain Dependency Inversion Principle (DIP) in detail
Assistant
The Dependency Inversion Principle (DIP) changes how high-level application logic interacts with low-level implementation details to build flexible, loosely coupled software.
Core Definition
  1. High-level modules should not depend on low-level modules. Both should depend on abstractions.
  2. Abstractions should not depend on details. Details depend on abstractions.
Key Concepts
  • High-Level Modules: Core business logic (e.g., OrderService, PaymentProcessor).
  • Low-Level Modules: Utility components/DB tools (e.g., MySQLDatabase, SendGridEmailClient).
  • Abstractions: Interfaces or abstract classes defining *what* needs to be done.
Practical Java Example

1. The Violation

public class MySQLDatabase {
    public void saveOrder(String orderId) {
        System.out.println("Saving order " + orderId + " to MySQL DB");
    }
}

public class OrderService {
    private MySQLDatabase database;

    public OrderService() {
        this.database = new MySQLDatabase(); // Tightly coupled
    }

    public void processOrder(String orderId) {
        database.saveOrder(orderId);
    }
}

2. The Solution (Applying DIP)

public interface OrderRepository {
    void save(String orderId);
}

public class MySQLRepository implements OrderRepository {
    public void save(String orderId) { System.out.println("Saving to MySQL"); }
}

public class MongoRepository implements OrderRepository {
    public void save(String orderId) { System.out.println("Saving to MongoDB"); }
}

public class OrderService {
    private final OrderRepository repository;

    // Constructor Injection
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    public void processOrder(String orderId) {
        repository.save(orderId);
    }
}

How to create an Immutable Class and why it’s thread-safe.
Assistant
An Immutable Class is a class whose instances cannot be modified after creation.
5 Rules to Create an Immutable Class
  1. Declare class as final.
  2. Make all fields private and final.
  3. Do not provide setter methods.
  4. Initialize all fields via constructor performing deep copies for mutable objects.
  5. Return deep copies of mutable objects in getters (defensive copying).
import java.util.Date;

public final class Employee {
    private final int id;
    private final String name;
    private final Date joiningDate; // Mutable object

    public Employee(int id, String name, Date joiningDate) {
        this.id = id;
        this.name = name;
        this.joiningDate = new Date(joiningDate.getTime()); // Defensive copy
    }

    public int getId() { return id; }
    public String getName() { return name; }
    
    public Date getJoiningDate() {
        return new Date(joiningDate.getTime()); // Defensive copy
    }
}
Why Immutable Classes Are Thread-Safe
  • Read-Only Access: Concurrent threads can safely read simultaneously without locking.
  • No Race Conditions: Internal state cannot be corrupted post-construction.
  • Guaranteed Safe Publication: final field semantics in JMM guarantee full visibility once constructed.

HashMap internal working — hashing, collision, resizing.
Assistant
HashMap is a key-value data structure using a hybrid Node Array + Singly Linked List + Red-Black Tree (Java 8+).
1. Hashing & Bucket Index Calculation $$\text{hash} = h \oplus (h \gg 16)$$ $$\text{index} = (n - 1) \ \& \ \text{hash}$$
2. Collision & Treeification
  • Chaining: Uses Linked Lists for colliding keys.
  • Treeification: Bucket converts to a Red-Black Tree when nodes ≥ 8 and capacity ≥ 64. Reduces lookup time from $O(n)$ to $O(\log n)$.
  • Untreeification: Reverts to list when bucket nodes drop ≤ 6.
3. Resizing Algorithm
  • Triggers when entries exceed $\text{Capacity} \times \text{Load Factor}$ (Default $16 \times 0.75 = 12$).
  • Capacity doubles ($16 \rightarrow 32$). Re-indexing checks (hash & oldCap) == 0 to split nodes cleanly without full hash re-computation.

Example Calculation: Key = `"John"`, Capacity $n = 16$.
  • Step 1: hashCode(): "John".hashCode() = 2314539
    Binary: 00000000 00100011 01010001 00101011
  • Step 2: Spread Hash: h ^ (h >>> 16)
    Calculated Hash: 2314504
    Binary: 00000000 00100011 01010001 00001000
  • Step 3: Index Masking: (16 - 1) & hash
    Index Binary: 00000000 00000000 00000000 00001000 = Decimal 8 
public class HashCalc {
    public static void main(String[] args) {
        String key = "John";
        int n = 16;
        int h = key.hashCode();
        int hash = h ^ (h >>> 16);
        int index = (n - 1) & hash;
        System.out.println("Index: " + index); // Prints 8
    }
}

Explain Java Memory Model (JMM) and volatile.
Assistant
The Java Memory Model (JMM) defines how threads interact through memory, handling variable visibility, instruction reordering, and memory barriers.
Core Concepts
  • Working Memory vs Main Memory: Threads copy variables into local CPU caches (Working Memory). Updates might not immediately write back to RAM (Main Memory), causing visibility issues.
  • Happens-Before Relationship: Guarantees that memory writes by one thread are visible to reads by another.
The volatile Keyword
  1. Guarantees Visibility: All reads/writes go straight to Main Memory.
  2. Prevents Instruction Reordering: Inserts memory barriers to stop CPU compiler optimizations from shifting instructions across volatile boundaries.

How to perform multi-level sorting using Comparator.
Assistant
Multi-level sorting is performed by chaining Comparator.comparing() with .thenComparing(). 
import java.util.*;

public class MultiSort {
    public static void main(String[] args) {
        List<Employee> list = Arrays.asList(
            new Employee("IT", "Alice", 90000),
            new Employee("HR", "Bob", 60000),
            new Employee("IT", "Charlie", 95000),
            new Employee("IT", "David", 90000)
        );

        Comparator<Employee> comp = Comparator
                .comparing(Employee::getDepartment)                         // 1st Level: Dept ASC
                .thenComparing(Employee::getSalary, Comparator.reverseOrder()) // 2nd Level: Salary DESC
                .thenComparing(Employee::getName);                           // 3rd Level: Name ASC

        list.sort(comp);
        list.forEach(System.out::println);
    }
}
